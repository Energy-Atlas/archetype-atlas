# Autonomous Agent Brief — Building Energy Archetype Parameter Atlas

## 1. Project purpose

This repository will build a **machine-readable building-energy archetype parameter atlas** to support research on geometric and thermal-zoning levels of detail in urban building energy modeling (UBEM).

The research does **not** aim to reproduce the statistical frequency of the U.S. building stock. Instead, it aims to cover a broad, physically plausible and reproducible range of building-energy conditions so that geometric/zoning simplifications can be tested across many building typologies, programs, climates, vintages, schedules, envelope conditions, and HVAC configurations.

The geometric part of the research is handled separately by parametric plan generators. These generators define building plan topology, zone boundaries, adjacency, orientation, dimensions, floor count, unit count, corridors, stairs, cores, conditioned/unconditioned zones, and other geometric features.

This repository should therefore focus on the **energy semantics** needed to instantiate those geometric models.

---

## 2. Research context

The larger study evaluates how much modeling accuracy is lost when a detailed multi-zone reference model is simplified using different geometric/zoning methods.

Typical building categories include, but are not limited to:

- multifamily/apartment buildings;
- offices;
- hotels;
- strip malls;
- retail;
- restaurants;
- supermarkets/markets;
- high-rise commercial buildings;
- other multi-zone commercial or mixed-program archetypes.

Single-family homes are lower priority because the research question is primarily about buildings where alternative zoning abstractions are meaningful.

For each parametric building typology, the study may test multiple program mixes and multiple dimensional configurations. A detailed unit/program-level EnergyPlus-style model is used as the **reference model**. Simplified models may include, for example:

- merging repeated units;
- ASHRAE-style perimeter/core zoning;
- other perimeter/core abstractions;
- floor-as-one-zone;
- floor multipliers;
- whole-building single-zone approximations;
- other reduced zoning or geometric representations.

The objective is to derive a guideline that tells a user what geometric/zoning level of detail is sufficient for a given combination of typology, program mix, climate/weather, envelope characteristics, schedules, loads, and HVAC conditions.

---

## 3. Primary task for the agent

Research, extract, normalize, document, and version **building-energy input archetypes** that can be assigned to zones/programs generated by the geometry atlas.

The preferred modern sources are:

1. **ComStock** for commercial-building stock characteristics, model-generation rules, program/space-type assumptions, schedules, envelope characteristics, HVAC/system assumptions, and existing-stock variation.
2. **ResStock** for residential and multifamily dwelling-unit characteristics, especially occupancy, thermostat settings, plug/appliance loads, infiltration, envelope properties, and residential HVAC.
3. **OpenStudio Standards / related PNNL standards datasets** for program/space-type definitions, internal loads, schedules, ventilation, constructions, HVAC, and code/template metadata used downstream by ComStock or DOE prototype workflows.
4. **DOE Commercial Reference Buildings** as legacy existing-stock benchmark archetypes, especially the pre-1980 and post-1980 categories.
5. **DOE/PNNL Prototype Building Models** as new-construction/code-compliant benchmark archetypes across successive ASHRAE 90.1 / IECC vintages.
6. **CBECS or other national survey data** as supporting evidence or validation when useful, but not as the main source of program-level BEM parameters.

Do not assume one source contains everything. The agent should determine where each parameter actually originates and should preserve source provenance.

---

## 4. Conceptual data model

The initial expected structure is described below, but the agent may revise or normalize it after inspecting the source data. Any structural change should be documented with rationale.

### 4.1 Program archetype table

This table represents the energy semantics of a program/space type.

Expected fields include:

- `building_type`
- `program`
- `vintage_or_template`
- `variant`
- `people_density`
- `occupancy_schedule_id`
- `lighting_power_density`
- `lighting_schedule_id`
- `equipment_power_density`
- `equipment_schedule_id`
- `gas_equipment_power_density` or equivalent, where applicable
- `gas_equipment_schedule_id`
- `heating_setpoint_schedule_id`
- `cooling_setpoint_schedule_id`
- `ventilation_rate`
- other program-specific fields found to be materially relevant

Examples of `program` may include:

- office;
- guest room;
- apartment unit;
- corridor;
- lobby;
- retail;
- restaurant dining;
- kitchen;
- storage;
- staircase;
- mechanical/support;
- other archetypal programs actually defined by the source models.

The project does **not** require architectural room-by-room detail such as individual copy rooms or conference rooms unless the source archetype itself treats them as distinct energy programs.

### 4.2 Construction/envelope archetype table

Expected fields include:

- `vintage_or_template`
- `climate_zone`
- `variant`
- `wall_u_value`
- `roof_u_value`
- `floor_u_value`
- `window_u_value`
- `window_shgc`
- `window_vt`, if useful
- `infiltration`
- `infiltration_basis`
- other relevant construction metadata

This table should remain separate from program data unless source structure strongly suggests otherwise.

### 4.3 System archetype table

Expected fields include:

- `building_type`
- `vintage_or_template`
- `climate_zone`
- `variant`
- `system_type`
- `heating_type`
- `heating_fuel`
- `cooling_type`
- `efficiency_or_cop`
- `zone_terminal_type`
- `ventilation_strategy`
- `system_schedule_id`, where relevant
- other important system-level metadata

### 4.4 Building-to-program mapping table

Expected fields include:

- `building_type`
- `program`
- `area_fraction`
- `multiplicity`, where applicable
- `conditioned`
- `system_assignment`
- `source`
- `notes`

The agent should determine whether area fraction, multiplicity, or both are appropriate based on source data.

### 4.5 Schedule table(s)

Schedules should be stored in machine-readable form and referenced by IDs rather than duplicated into every program row.

Possible structure:

- `schedule_id`
- `schedule_type`
- `time_resolution`
- `weekday_profile`
- `weekend_profile`
- `seasonal_or_monthly_modifiers`
- `source`
- `template_or_vintage`
- `notes`

If annual 8760 schedules are the most faithful representation, store them in a compact machine-readable format and keep a metadata index.

## 5. Deterministic archetypes, not probability distributions, as the baseline

The baseline deliverable should consist of **deterministic archetype rows**.

Do not make the primary representation:

`LPD ~ distribution`, `ACH ~ distribution`, etc.

Instead, prefer explicit rows or variants such as:

- `Office / DOE Ref Pre-1980 / default`
- `Office / DOE Ref 1980-2004 / default`
- `Office / 90.1-2007 / default`
- `Office / existing-stock variant A`
- `Office / existing-stock variant B`

If useful distributions exist in ComStock or ResStock, preserve them as metadata or source evidence. They may later be used to define low/typical/high or other deterministic variants, but the primary atlas should remain reproducible and directly enumerable.

The broader research values **coverage of plausible conditions more than population weighting**.

---

## 6. Climate and vintage handling

Do not duplicate identical program data across climate zones simply to create a full Cartesian table.

Prefer normalized relationships such as:

- program properties: primarily conditioned on program/building type and vintage/template;
- envelope properties: primarily conditioned on vintage/template and climate zone;
- system properties: conditioned on building type, vintage/template, climate zone, and system variant;
- weather: handled separately by EPW/climate inputs.

Preserve physically meaningful dependencies. Do not enforce stock prevalence correlations that are irrelevant to the experimental purpose.

The working principle is:

> Preserve physical feasibility and source-defined dependencies; do not preserve prevalence merely for statistical representativeness.

---

## 7. Source interpretation

The agent should distinguish among:

### Existing-stock archetypes
Use DOE Commercial Reference Buildings, ComStock resources, and ResStock resources as appropriate.

### New-construction/code archetypes
Use DOE/PNNL Prototype Building Models and standards datasets.

### Statistical stock evidence
Use ComStock/ResStock distributions and CBECS to understand plausible ranges or validate selected variants.

### Program/space-type semantics
Use OpenStudio Standards, ComStock model-generation resources, PNNL standards databases, or equivalent source definitions.

A historical code-compliant model should not automatically be treated as equivalent to an existing building of the same age. Existing buildings may have deterioration, retrofits, equipment replacements, envelope changes, and altered schedules. Keep this distinction explicit in documentation.

---

## 8. Expected output quality

All generated tables must be:

- machine-readable;
- human-inspectable;
- version controlled;
- reproducible;
- source-traceable;
- unit-consistent;
- documented;
- stable enough to support downstream simulation generation.

Prefer plain-text formats such as:

- CSV;
- TSV;
- JSON;
- YAML;
- Parquet only when needed for size/performance, with a plain-text schema and export.

Do not use an opaque database file as the only canonical representation.

A database may be generated from canonical tabular files, but canonical research data should remain diffable in Git where practical.

---

## 9. Provenance requirements

Every extracted or normalized record should preserve enough information to trace it back to its source.

At minimum, include or maintain:

- source project;
- source repository or URL;
- source file path;
- source version/tag/commit when available;
- original field name;
- original units;
- transformation applied;
- extraction date;
- notes on assumptions;
- confidence or interpretation note when source semantics are ambiguous.

If a value is derived rather than directly reported, mark it clearly.

Never silently substitute an assumption for missing data.

---

## 10. Versioning and releases

The repository should support multiple data releases.

Recommended structure:

```text
data/
  raw/
  interim/
  processed/
  releases/
    v0.1.0/
    v0.2.0/
```

Or an equivalent structure chosen by the agent.

Rules:

- Raw downloaded source files should be immutable once committed, unless licensing or size constraints require scripts instead.
- Transformations should be scripted.
- Processed canonical tables should be reproducible from raw/interim data.
- Release notes should describe schema changes, source changes, and material corrections.
- Use semantic versioning where practical.
- Schema-breaking changes require clear migration notes.

For large files that should not be committed, include download scripts and checksums instead.

## 12. Security and public-repository rules

This repository is intended to be public.

Never commit:

- API keys;
- access tokens;
- passwords;
- private URLs containing credentials;
- local authentication files;
- personally identifiable information;
- proprietary data without permission;
- files whose license prohibits redistribution.

If a source requires credentials or manual download, document the process and provide a script/template that uses local environment variables.

Before every commit, inspect staged changes for accidental secrets.

## 13. Agent autonomy

The agent is expected to work autonomously after a short initial clarification stage.

### Initial clarification

The agent may ask a few concise rounds of questions at the beginning if essential decisions are genuinely ambiguous.

After that, proceed independently.

Do not repeatedly stop for approval on ordinary implementation choices.

When uncertain:

1. inspect source documentation;
2. record the uncertainty;
3. choose the most defensible reversible implementation;
4. document the choice;
5. continue.

Escalate only when the choice would materially change the scientific interpretation, licensing status, public-release feasibility, or overall project architecture.

---

## 14. Agent responsibilities

The agent should autonomously:

- search and inspect source repositories and official datasets;
- determine where required parameters actually reside;
- download or script retrieval of relevant data;
- design normalized schemas;
- write parsers and transformation scripts;
- validate units and definitions;
- resolve duplicates;
- document provenance;
- generate canonical tables;
- create tests or validation checks;
- compare extracted values against reference/prototype models where useful;
- document gaps and unresolved ambiguities;
- maintain the repo structure;
- make commits as logical units of work;
- maintain changelogs/release notes when appropriate.

The agent may revise the proposed schema if source inspection shows a better representation.

Any meaningful schema revision should be documented in an ADR, issue, design note, or commit message.

## 15. Git and commit rules

The agent may commit freely as work progresses.

Use Conventional Commits-style messages, for example:

```text
feat(schema): add program archetype tables
fix(schedules): correct weekday profile normalization
data(comstock): add extracted office program parameters
docs(sources): document reference building provenance
refactor(parser): normalize unit conversion pipeline
test(validation): add schedule consistency checks
chore(repo): initialize environment templates
```

Preferred structure:

```text
<type>(<scope>): <imperative description>
```

Keep commits focused and reversible.

### Commit authorship

The agent must explicitly identify the automated agent/model used for each commit.

Do this through Git author identity and/or a commit trailer. Example:

```text
Author: Research Agent <agent@example.invalid>

Agent-Model: <provider/model-name>
Agent-Variant: <variant or reasoning mode if applicable>
```

If the environment supports only standard Git metadata, use a neutral automated-agent author and include model information in commit trailers.

Do not impersonate a human user as the author.

Do not expose private account information in commit metadata.

## 17. Validation requirements

At minimum, implement checks for:

- missing required fields;
- duplicate primary keys;
- invalid units;
- negative or impossible physical values;
- schedule values outside expected bounds;
- schedule length/time-resolution consistency;
- heating setpoint above cooling setpoint when such a condition is unintended;
- invalid U-values, SHGC, efficiencies, or infiltration values;
- invalid program/building-type mappings;
- orphan foreign keys;
- missing provenance;
- inconsistent vintage/climate labels.

Where a source provides a complete EnergyPlus/OpenStudio model, compare normalized outputs against the source model or published scorecard when practical.

---

## 18. Scientific scope boundaries

Do not spend effort reconstructing detailed architectural room layouts.

The required resolution is approximately the level of DOE Commercial Reference Buildings / Prototype Buildings:

- program/space-type separation;
- representative zone-level internal loads;
- schedules;
- setpoints;
- ventilation;
- envelope;
- infiltration;
- HVAC/system assignment.

Repeated units may have identical metadata while differing geometrically.

The geometry atlas will handle spatial arrangement.

The energy atlas should supply the semantics assigned to those generated zones.

---

## 19. Recommended implementation strategy

A reasonable autonomous sequence is:

1. Initialize repository and documentation.
2. Inventory ComStock, ResStock, OpenStudio Standards, DOE Reference Buildings, and PNNL Prototype sources.
3. Build a source-to-parameter matrix.
4. Identify canonical program vocabulary.
5. Draft normalized schema.
6. Implement extraction for one representative archetype, such as Medium Office.
7. Validate the complete pipeline end-to-end.
8. Extend across commercial archetypes.
9. Add multifamily/residential parameters from ResStock.
10. Add envelope/system/vintage/climate mappings.
11. Add reference/prototype benchmark comparisons.
12. Produce the first versioned release.
13. Document coverage gaps and future extensions.

Do not attempt to ingest everything before validating the schema on a small number of representative archetypes.

---

## 20. Definition of a successful first release

A useful first release should provide:

- a stable normalized schema;
- deterministic program archetype rows;
- schedules referenced by IDs;
- construction/envelope archetypes by vintage and climate;
- system archetypes;
- building-to-program mappings;
- provenance for every major data source;
- scripts that reproduce the processed tables;
- validation tests;
- documentation of coverage and known limitations;
- at least a meaningful subset of major commercial archetypes plus multifamily/apartment support.

The first release does not need to be statistically representative of the national stock.

It must instead be scientifically interpretable, reproducible, and sufficiently broad to support the zoning-LOD experiment.

---

## 21. Guiding principle

The repository should answer:

> Given a building typology, program, vintage/template, climate, and system condition, what deterministic zone-level energy semantics should be assigned to the geometry generated by the typology atlas?

The project should remain modular enough that later work can add:

- distributions;
- low/typical/high variants;
- regional calibration;
- retrofit states;
- deterioration states;
- alternative schedules;
- additional national datasets.

Those extensions should not be required to make the baseline atlas useful.
