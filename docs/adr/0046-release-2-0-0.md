# ADR 0046: Release 2.0.0, a full snapshot that ends the delta chain

Status: phase 1 accepted (2026-10-27); phase 2 approved (2026-10-27), run as plan stages X1.1–X1.4.
Stage X1 of plan `docs/superpowers/plans/2026-10-27-stages-after-release-1-4-0.md`
(user decision X-1, 2026-10-27: a full snapshot after the data stages; X-2: 1.x
verify-only; X-3: recipes only for the families that have them; P1: openstudio-standards
stays the 90.1 construction authority).

## 1. Context

- Releases 1.1.0 to 1.6.0 are deltas on 1.0.0, and each holds every change since 1.0.0.
  The six deltas take about 1.1 GB on top of 1.0.0's 216 MB, and their builder is one
  file of tagged blocks, so earlier releases still verify against the bytes that wrote
  them.
- Pinned writers (`scripts/atlas_programs.py`, `atlas_constructions.py`,
  `prototype_dwellings.py`, `residential_exports.py`, …) are patched around for each
  release; release enums hard-coded in them need wrappers (`later_residential`).
- The generator recipes (`atlas_schedules/data/recipes/`, 1,900 files) are keyed by the
  frozen definition IDs of `data/definition-releases/v0.1.1`, not by release IDs.
- The site, about 40 scripts and many tests still read the frozen v0.x and v1–v2
  folders under `data/` (about 890 MB).

## 2. Decisions (phase 1)

1. **Release 2.0.0 is the resolved release 1.6.0, stored whole** (`scripts.atlas_snapshot`):
   no base release; later minors will be deltas on it. Every value is the 1.6.0 value:
   each resolved 1.6.0 JSON file decodes to the same JSON in 2.0.0
   (`tests/test_release_2_0_0.py`).
2. **Compact storage (P9).** Indented JSON files are re-encoded one record per line
   down to three levels; line tables stay as they are. The resolved 1.6.0 tree of
   439 MB becomes 337 MB.
3. **Generator recipes beside the programs (X-3, P8).** Each 90.1 folder gets a
   `generator.json` keyed by release program ID, with the source and reviewed recipe
   of the program's definitions. 610 programs, all leaf and mix programs of the
   90.1 templates since 1.0.0, carry recipes.
4. **Exports** of 2.0.0 are those of 1.6.0, with `atlas-release-2.0.0` added to the
   release enums of Program JSON 5.1.0, 5.2.0 and 5.4.0, building services and source
   model constructions.

## 3. Agent decisions

1. **Snapshot by transformation, not by new writers.** *Alternative:* rewrite the
   writers first (phase 2). *Reason:* the writers' pins, the frozen folders and the
   site are intertwined (section 4); a snapshot of the verified 1.6.0 tree ends the
   delta chain now, with inputs pinned (1.6.0 manifest, recipes digest, builder).
2. **Recipes in `generator.json`, not inside the program files.** *Reason:* program IDs
   hash program content, so adding the recipe to a program file would change every 90.1
   program ID and every file that cites one, with no value change. The recipe sits
   one folder up, keyed by the unchanged ID.
3. **No recipes for DOE Ref programs.** They come from the 1.0.0 definitions, but
   release 1.1.0 changed the DOE Ref schedules and loads (ADR 0037), so their recipes
   are stale. The construction-only, IECC, plenum and residential programs never had
   recipes. Both are listed as deferred in the manifest.
4. **The 2.0.0 folder is not committed yet** (section 4, item 1).

## 4. Phase 2 and its blocking conditions

1. **Committing 2.0.0 (337 MB).** Committing it before the deltas leave the tree only
   grows the repository. It should land with item 3. *Needs:* your go-ahead.
2. **Recipes for DOE Ref and the later families.** They must be regenerated from the
   release programs. *Decided* (2026-10-27): regenerate them (plan stage X1.2). The
   earlier note here, that the generator's answer keys hold no DOE Ref cases, was wrong:
   the native and legacy keys capture the DOE Ref recipes of the frozen definitions
   (section 6).
3. **Retire the frozen folders to tags (X-2).** The current site build reads
   `data/releases/v0.1.0`, `v0.2.0` and `data/definition-releases/v0.1.1`. Stage S
   replaces that site. After S merges: tag the folders, delete them from the tree,
   make the 1.x checks verify-only (checksums without input digests), and rewire the
   tests that read them. *Needs:* S merged.
4. **Rewritten writers.** Writers that read and write the 2.0.0 layout directly, with
   new pins; selection decisions moved to the evidence tree; release enums no longer
   hard-coded. *Needs:* item 3, so the old pins can lapse.
5. **P1 applied.** The 90.1 sets keep openstudio-standards constructions (already
   true). Recording the prototype assemblies as alternates where U or SHGC differ by
   more than 1% needs a construction alternates field, which the writers of item 4
   should add.

## 5. Phase 2, stage X1.1: a self-contained 2.0.0

Every `atlas_exports.Release`, 2.0.0 included, read the frozen folders at run time:
release verification re-hashed their manifests, filled exports read
`data/definition-releases/v0.1.1` to match the capped-delivery demands (ADR 0018), and
the source exporter read `data/releases/v0.2.0/programs.json` for the programs with no
setpoint schedules. So the folders could not go.

1. **`exporter-inputs.json` at the release root** carries what the exporters took from
   the frozen folders, under release IDs: 3 capped services, 3 capped programs, and the
   43 source programs with neither setpoint schedule. It sits outside `evidence/`,
   whose files the exporters read as provenance rows.
2. **Readers verify the files alone.** `atlas_snapshot.files()` checks every file
   against the manifest; `--verify` and `--check` still compare the writer's inputs.
3. **The exporters take the carried values.** `Release` passes them to the commercial
   exporters. The residential exporters are built by `residential_exports`, which
   releases 1.4.0 to 1.6.0 pin, so `Release` sets `program_json_v3.INACTIVE_CONTROLS`
   for the length of a dwelling export, like `later_residential` (until stage X1.4).
4. **Evidence:** with every frozen folder and the 1.x releases moved away, release
   2.0.0 exports every sampled program, dwelling and construction; the refusals are the
   documented source-only cases. 808 source and filled exports equal release 1.6.0's.
   `tests/test_release_2_0_0.py` fails if an export opens a frozen folder.

## 6. Milestone A: stages X1.2 and X1.2a

Milestone A runs X1.2 to X1.3 on one branch with one PR (user, 2026-10-27).

**X1.2, DOE Ref recipes from the release.**

1. `scripts/build_reference_recipes.py` writes the DOE Ref recipes from release 2.0.0:
   - source records under their release IDs;
   - schedules under their release schedule IDs, added to the generator's
     `schedules.json`;
   - the shared hot-water services of each folder.

   It replaces the 672 recipes, 60 configurations and 54 services that
   `build_family_recipes` had built from the frozen definitions (release 1.0.0
   values), and removes the 165 schedule entries only those used. The new set is 279
   commercial, 72 composition, 2 apartment-unit and 4 fixed recipes, 30
   configurations, 54 services and 422 schedules.
2. **People topology from the DOE file zones** (Chicago 5A IDFs, checked against the
   reconciliation register). Each zone maps to its release program as the
   reconciliation compared them, and counts zone floor area times the program's
   occupancy density. The totals equal the frozen recipes' except where release
   1.1.0 changed the building:
   - the Large Office basement has half the office occupancy (671 against 767
     people);
   - the Supermarket's aliased sales zones count 368 against 385 people;
   - the Primary School computer room differs by 0.1 person.
3. `generator.json` of every DOE Ref folder carries the source recipes. 967 programs
   now have recipes (610 90.1, 357 DOE Ref).
4. **Checks.**
   - `tests/test_reference_recipes.py`: every demand, slot, density, setpoint,
     composition and water service equals its release value, and every schedule
     equals its release rules.
   - `--check` reproduces the files where the IDFs are present
     (`ATLAS_DOE_REFERENCE_ROOT`).
   - The catalogue smoke generates every recipe.

**X1.2a, daylighting as plain values** (user, L-1). 2.0.0 drops
`lighting_controls.geometry_dependent` from the 1,373 programs that carried it
(`counts.plain_daylighting_programs`). Consumers apply the fractions as given; BEMGen's
side is `docs/bemgen-handoff-release-2-0-0.md`.

**Agent decisions.**

1. **Program IDs stay those of 1.6.0.** Dropping the flag changes 1,373 program files,
   and by the 1.x writers' rule (ADR 0036) their IDs hash content. *Alternative:*
   re-hash them now with a 1.6.0 to 2.0.0 map, which cascades into mixes and every
   file that cites them. *Reason:* milestone B's rewritten writers re-derive every ID
   with one published map (U). Re-hashing now would give consumers two ID changes
   instead of one. Readers verify files by checksum, not IDs by content.
2. **Source recipes only for DOE Ref.** The release keeps no reviewed DOE Ref view.
   For the generated types, its fills set only zero loads and the conditioning of
   unconditioned attics and plenums, none of which carries a slot. *Alternative:* a
   filled recipe per program, identical in slots.
3. **The generator request accepts release IDs.** `request-v2.schema.json` widens the
   `program_id` and `service_id` patterns to `program-…`/`service-…` or a release ID.
   Requests valid before stay valid; the schema version is unchanged.
4. **The answer keys keep their DOE Ref captures, and the tests skip them.** The native
   keys and the frozen v0.8.0 legacy keys capture the replaced recipes on release 1.0.0
   inputs:

   | Key | Captured DOE Ref inputs |
   | --- | --- |
   | `families` | 66 programs |
   | `family-programmes` | 96 programs |
   | `occupancy-dominance` | 60 configurations |
   | case matrix, programmes and mixtures | 82, 66 and 1 programs |

   No native capture exists for the release values. Recording one would mean building
   ComStock models of the DOE files.
   - `tests/answer_keys/retired-doe-ref.json` lists the replaced IDs.
   - The tests skip the cases that name them; the dominance test asserts that exactly
     60 are skipped.
   - The 90.1 cases of the same 15 sampling types keep checking the port.

   *Alternative:* keep the replaced recipes as test fixtures, which would mean a second
   data root in the generator.
5. **Midrise Apartment** recipes keep the shape of the frozen ones: the apartments as an
   apartment unit with caller water, the office and corridor as fixed source rule sets.
   Water sensible and latent fractions come from the release where it states them,
   else from openstudio-standards' constants (0.2 and 0.05), as before.
6. **The DOE Ref types without a sampling building type** (College, Courthouse, the
   detailed offices and Office) have no recipes, as before; the manifest lists them as
   deferred.
