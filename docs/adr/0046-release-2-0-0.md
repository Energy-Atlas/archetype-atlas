# ADR 0046: Release 2.0.0, a full snapshot that ends the delta chain

Status: phase 1 accepted (2026-10-27); phase 2 approved (2026-10-27), run as plan stages X1.1–X1.3 and
milestone B; release 2.0.0 declared released in milestone B (2026-10-28, section 10).
Stage X1 of plan `docs/superpowers/plans/2026-10-27-stages-after-release-1-4-0.md`
(user decision X-1, 2026-10-27: a full snapshot after the data stages; X-2: 1.x
verify-only; X-3: recipes only for the families that have them; P1: openstudio-standards
stays the 90.1 construction authority).

## 1. Context

- Releases 1.1.0 to 1.6.0 are deltas on 1.0.0, and each holds every change since 1.0.0.
  The six deltas take about 1.1 GB on top of 1.0.0's 216 MB, and their builder is one
  file of tagged blocks, so earlier releases still verify against the bytes that wrote
  them.
- Pinned writers (`scripts/atlas_programs.py`, `atlas_constructions.py`,
  `prototype_dwellings.py`, `residential_exports.py`, …) are patched around for each
  release; release enums hard-coded in them need wrappers (`later_residential`).
- The generator recipes (`atlas_schedules/data/recipes/`, 1,900 files) are keyed by the
  frozen definition IDs of `data/definition-releases/v0.1.1`, not by release IDs.
- The site, about 40 scripts and many tests still read the frozen v0.x and v1–v2
  folders under `data/` (about 890 MB).

## 2. Decisions (phase 1)

1. **Release 2.0.0 is the resolved release 1.6.0, stored whole** (`scripts.atlas_snapshot`):
   no base release; later minors will be deltas on it. Every value is the 1.6.0 value:
   each resolved 1.6.0 JSON file decodes to the same JSON in 2.0.0
   (`tests/test_release_2_0_0.py`).
2. **Compact storage (P9).** Indented JSON files are re-encoded one record per line
   down to three levels; line tables stay as they are. The resolved 1.6.0 tree of
   439 MB becomes 337 MB.
3. **Generator recipes beside the programs (X-3, P8).** Each 90.1 folder gets a
   `generator.json` keyed by release program ID, with the source and reviewed recipe
   of the program's definitions. 610 programs, all leaf and mix programs of the
   90.1 templates since 1.0.0, carry recipes.
4. **Exports** of 2.0.0 are those of 1.6.0, with `atlas-release-2.0.0` added to the
   release enums of Program JSON 5.1.0, 5.2.0 and 5.4.0, building services and source
   model constructions.

Amended by [ADR 0051](0051-generation-parameters-in-the-release.md) (2026-10-29): release 2.2.0,
a delta on 2.1.0, removes every folder's `generator.json` (decision 3 and section 6, item 3) and
carries the generation parameters as program blocks in each folder's `generation.json`.

## 3. Agent decisions

1. **Snapshot by transformation, not by new writers.** *Alternative:* rewrite the
   writers first (phase 2). *Reason:* the writers' pins, the frozen folders and the
   site are intertwined (section 4); a snapshot of the verified 1.6.0 tree ends the
   delta chain now, with inputs pinned (1.6.0 manifest, recipes digest, builder).
2. **Recipes in `generator.json`, not inside the program files.** *Reason:* program IDs
   hash program content, so adding the recipe to a program file would change every 90.1
   program ID and every file that cites one, with no value change. The recipe sits
   one folder up, keyed by the unchanged ID. *Superseded by
   [ADR 0051](0051-generation-parameters-in-the-release.md):* the ID rule leaves the program's
   `generation` block out, so the parameters travel with the program.
3. **No recipes for DOE Ref programs.** They come from the 1.0.0 definitions, but
   release 1.1.0 changed the DOE Ref schedules and loads (ADR 0037), so their recipes
   are stale. The construction-only, IECC, plenum and residential programs never had
   recipes. Both are listed as deferred in the manifest.
4. **The 2.0.0 folder is not committed yet** (section 4, item 1).

## 5. Phase 2, stage X1.1: a self-contained 2.0.0

Every `atlas_exports.Release`, 2.0.0 included, read the frozen folders at run time:
release verification re-hashed their manifests, filled exports read
`data/definition-releases/v0.1.1` to match the capped-delivery demands (ADR 0018), and
the source exporter read `data/releases/v0.2.0/programs.json` for the programs with no
setpoint schedules. So the folders could not go.

1. **`exporter-inputs.json` at the release root** carries what the exporters took from
   the frozen folders, under release IDs: 3 capped services, 3 capped programs, and the
   43 source programs with neither setpoint schedule. It sits outside `evidence/`,
   whose files the exporters read as provenance rows.
2. **Readers verify the files alone.** `atlas_snapshot.files()` checks every file
   against the manifest; `--verify` and `--check` still compare the writer's inputs.
3. **The exporters take the carried values.** `Release` passes them to the commercial
   exporters. The residential exporters are built by `residential_exports`, which
   releases 1.4.0 to 1.6.0 pin, so `Release` sets `program_json_v3.INACTIVE_CONTROLS`
   for the length of a dwelling export, like `later_residential` (until stage X1.4).
4. **Evidence:** with every frozen folder and the 1.x releases moved away, release
   2.0.0 exports every sampled program, dwelling and construction; the refusals are the
   documented source-only cases. 808 source and filled exports equal release 1.6.0's.
   `tests/test_release_2_0_0.py` fails if an export opens a frozen folder.

## 8. Milestone B: stages B4 and B1, one ID change

The user decided on 2026-10-28: correct 2.0.0 in place while it is `candidate`, with a release
editor rather than source rebuilders, and one PR for the milestone.

1. **The release editor** (`scripts/release_editor.py`). Release 2.0.0's writers left the tree in
   X1.3, so later changes edit the release itself. The editor:
   - reads the verified files;
   - re-derives every commercial content-hashed ID by rule;
   - rewrites every reference and renames files whose names are IDs;
   - rewrites the manifest and records the edit under `edited_by`.

   `--check` fails unless every ID already follows its rule. CI's release job runs it, and running
   the editor on its own output changes nothing.
2. **ID rules.** Each ID keeps its readable prefix; the last segment is `h6` of the content
   without `id` and `name`:

   | Records | Content hashed | Floats |
   | --- | --- | --- |
   | Library (materials, then assemblies citing materials by their new IDs) | the record | rounded to nine significant digits |
   | Construction sets | the set, with every set ID written as one placeholder | rounded to nine significant digits |
   | Programs (source programs, then mixes until no ID moves) | the program without `generation` ([ADR 0051](0051-generation-parameters-in-the-release.md)), with service citations written as one placeholder | exact |

   The fitted unified assemblies differ in the last bits between interpreters and math libraries,
   which is why the 90.1 releases needed the pinned CPython 3.14.7 (user decision U). Program values
   come from IEEE arithmetic on source values and hash exactly; this is the rule
   `atlas_programs.program_id` already applied.
3. **The change.** 11,507 IDs were re-derived:
   - most library and set IDs, because of the rounding;
   - the 1,373 programs whose daylighting flag was dropped in milestone A;
   - 161 programs and 108 IECC mixes that later overlays had changed after their IDs were assigned.

   2,056 files are renamed. `id-map.json` at the release root maps every changed ID to its new one.
   The residential tree keeps its own IDs.
4. **Agent decisions.**
   1. **Twins merge.** 57 pairs of fitted assemblies (90.1 and DOE Ref) agree to nine significant
      digits and differ by at most 1.04e-9 relative. Under the rule they are one assembly, so each
      pair becomes one record: the one with the lower earlier ID. No list names both members of a
      pair; the editor refuses one that does. *Alternative:* a suffix to keep both. *Reason:* they
      are one assembly up to numerical noise, and the merged values move by at most 1e-9 relative.
   2. **Programs hash exactly**, without rounding. *Alternative:* round as the library does.
      *Reason:* their values are already interpreter-independent, so rounding would only add
      churn.
   3. **Service IDs, schedule IDs and the residential tree are not re-derived.** Their content did
      not change, and they hash no fitted values.
5. **Downstream.** The DOE Ref generator recipes of the 62 DOE Ref programs whose IDs moved are
   rewritten by `scripts/build_reference_recipes.py` (`--check` reproduces them). `generator.json`
   carries the same recipes.

## 9. Milestone B: stage B3, the PNNL prototype constructions as alternates

User decision P1 (2026-10-27): openstudio-standards stays the construction authority of the 90.1
templates, and the PNNL prototype assembly is recorded as an alternate where U or SHGC differ by more
than 1%.

1. **The input.** `python -m scripts.construction_alternates` reads the 912 pinned ASHRAE 90.1
   prototype IDFs (2007, 2013 and 2019; 16 types; 19 locations) and writes
   `data/program-inputs/construction-alternates-v1.json`. For each role:
   - it takes the prototype constructions by net area, with zone and window multipliers;
   - it compares them with the atlas building-default assembly of the context the IDF's
     `AnalysisClimateZone` names, as review S3 did: layer resistance without air films for opaque
     assemblies, U-factor and SHGC for glazing, F-factor for ground floors;
   - where any variant differs by more than 1%, it keeps every variant of the role with its area
     share and full IDF physics.

   It finds 2,722 component contexts (1,599 assemblies and 899 materials, each stored once).
   Ground floors agree everywhere. `--check` reproduces the input where the IDFs are present.
2. **The release edit.** `scripts/release_editor.py` applies the input before re-deriving IDs:
   - each set of a folder is compared with its own building default, and a differing role gets
     `alternates.<role>` in the context's detailed fields (the source, the compared atlas values,
     and the variants with area share, compared values, assembly ID and evidence);
   - the prototype assemblies and materials join the template library under the rule IDs of
     section 8 (`source_family: pnnl_prototype`);
   - their evidence rows join the folder's evidence file in the construction-document shape.

   Applying it again changes nothing.
3. **Detailed constructions 4.3.0**, an additive minor over 4.2.0, add the optional `alternates`.
   Every detailed export of release 2.0.0 declares 4.3.0.
4. **Agent decisions.**
   1. **Every variant of a differing role is recorded,** including variants that agree. *Reason:*
      the prototype's construction of the role is the set of variants with their shares, such as
      the per-floor walls `_grd`, `_mid` and `_top`.
   2. **Each set is compared on its own.** The small hotel of 90.1-2007 and 2013 holds a base set
      and an overlay that inherits from it; both get alternates against their own defaults.
      *Alternative:* the base set only.
   3. **Provenance as construction evidence rows** (project, revision, archive and IDF locator,
      file SHA-256), which the 4.x schema already requires. Program-style evidence with glossary
      terms was the alternative.
   4. **Fenestration areas include the zone multiplier** as well as the window multiplier. Review
      S3 counted the window multiplier only; the shares change, the roles that differ do not.

## 11. Erratum: the IECC ground floors (2026-10-28, after BEMGen's report)

BEMGen's receipt of 2.0.0 found that every IECC edition files some ground slabs under `InteriorFloor`
with a `Ground` condition and the F-factor ground method, contradicting that component's target
(`Surface`, `Adiabatic`). In the PNNL IECC models these slabs (Medium and Small Office core, 29
Outpatient slabs, the Primary School mechanical room, the Secondary School gym and mechanical room) have
the building's F-factor construction with `PerimeterExposed` 0 and an `Adiabatic` boundary: the
prototypes' way of giving a slab with no exposed edge no ground heat flow. Every F-factor floor with an
`Adiabatic` boundary in the 1,824 IECC models (all editions, the 16 types, 19 locations) has `PerimeterExposed` 0, and every one with a ground
boundary has a positive perimeter. The 1.x extractor filed the slabs by their boundary; its document
writer then added the ground condition because the construction is F-factor.

The user decided to correct 2.0.0 in place, since no consumer held it yet (BEMGen's branch was
unpushed), rather than build the delta reader a 2.0.1 would need. This narrows section 10 to one
recorded erratum; later changes still make a new release. `scripts/release_editor.py`
(`with_ground_floors`), in every IECC context:

1. **The slabs join the `GroundFloor` building default**, which holds the same assembly and ground
   method; a consumer's geometry supplies each slab's exposed perimeter, so a slab with none still
   gains no ground heat flow, and a re-zoned slab that reaches an edge does.
2. **The selection decision records the correction**: rule `source_boundary_correction`, the source
   boundary `Adiabatic`, and this decision.
3. **The zero-capacity slabs leave the interior floor capacity budgets** of both representations
   (0.197 m²/m² of counted floor area in the Medium Office). No capacity changes.
4. **The unified provenance no longer lists them as excluded interior floors.** They stay out of the
   floor mass, and no unified fit changes.

30 construction sets (5 types in 6 editions) change content and so their IDs. `id-map.json` maps
both their first-committed and their released IDs to the new ones (11,537 entries). The release stays
`released`. Agent decision: the slabs join the building default rather than a new `GroundFloor` rule,
since the source gives them the same construction; a separate rule was the alternative.

The same report raised three points that are not defects (recorded in
`docs/bemgen-handoff-release-2-0-0.md` section 4) and one schema drift, fixed without a data change:
the shared mass-accounting contract 1.1.0, derived from the definitions the constructions embed.

## 12. Release 2.1.0: the first delta on 2.0.0 (2026-10-29)

Release 2.1.0 is a delta on 2.0.0 (section 2 item 1; ADR 0036 section 2), written by
`scripts/atlas_delta.py` from pinned inputs (`--write`; `--check` rebuilds and compares;
`--verify` checks the folder and the base manifest). It holds only the files that differ:

1. **`LICENSE`**: the root open-licence text (ADR 0048 item 4) in place of the unlicensed text
   2.0.0 packaged.
2. **`generator.json` of the eight apartment folders** (90.1-2007, 2013 and 2019 Midrise and
   Highrise, DOE Ref Midrise): every apartment-unit recipe is the generator 3.0.0 ResStock
   multifamily unit recipe of the same program ID (ADR 0047 section 5), taken from the packaged
   recipes that `build_apartment_units` and `build_reference_recipes` write from 2.0.0. The
   other 1,506 recipes are byte for byte 2.0.0's.
3. **`manifest.json`**: `base_release` names 2.0.0 and its manifest's SHA-256; `generator` names
   the generator version, package, wheel and tag the recipes ship in (ADR 0049) and the recipes'
   digest; `input_sha256` pins the root licence, the version constant, the recipes, the base
   manifest and the writer. `removed` is empty; the counts are 2.0.0's.

Readers: `atlas_delta.files('2.1.0')` resolves the base and the delta (one base, never more);
`atlas_exports.Release` defaults to the newest release in the tree (`IN_TREE`), the export
schemas admit `atlas-release-2.1.0`, and the site shows 2.1.0. Program, construction and
service IDs are unchanged. Agent decisions: the delta writer rebuilds the eight files from the
packaged recipes rather than from a new recipe builder, since the packaged recipes are the
checked artefact (`build_apartment_units --check`, `build_reference_recipes --check`);
2.0.0's apartment prototype recipes remain the builders' input, so they keep reading 2.0.0.

Amended by [ADR 0051](0051-generation-parameters-in-the-release.md) (2026-10-29): the packaged
recipes this delta pinned left the tree with generator 4.0.0, so the manifest is edited in place
(`edited_by`) to pin the licence and the base manifest only, and `atlas_delta --check --release
2.1.0` rebuilds the licence, the README and the manifest around the `generator.json` files, which
are verified by checksum. Release 2.2.0 removes them and carries the same apartment units as
`resstock_unit` generation blocks.
