# ADR 0064: Release 2.5.0 (conditioning sides, per-side mixes, Program JSON 6.2.0, atlas-schedules 4.1.2)

Status: accepted (2026-11-04; stage AT5). It publishes the data and contract of
[ADR 0063](0063-conditioning-sides-and-per-side-mixes.md) and follows the mechanics of release 2.4.0
([ADR 0062](0062-release-2-4-0.md)). Decisions marked *agent decision* are this stage's.

## 1. The delta

Release 2.5.0 is a delta on 2.4.0 (ADR 0036 section 2, ADR 0046): `data/atlas-releases/v2.5.0` holds 792 files and the
manifest, and `removed` lists 518 paths of 2.4.0. The writer is `python -m scripts.atlas_delta --write --release
2.5.0`; `--check` rebuilds every file from its inputs and requires every program view to assemble (2,847).

- **The record edits** of ADR 0063: `scripts.atlas_edits_2_5_0.edit(files('2.4.0'))` gives the 788 files it changes or
  adds and the 518 paths it removes, the old names of the programs whose IDs move. The citing files follow the new IDs:
  the `generation.json` blocks, `services.json` beneficiaries, `definition-map.json` and `exporter-inputs.json`.
  - 72 source programs with a setpoint side no source equipment serves: the side an explicit null (`known`, value null),
    `parameters.conditioning` stated, one evidence row each with the HVAC map systems, the spaces and the replaced
    schedule (which stays in the folder's `schedules.json`);
  - every mix's `composition.setpoint_coverage` and per-side setpoints: 69 with a coverage below 1, 373 with full
    coverage (setpoints unchanged), 4 with an unknown side.
- **`id-map-2.5.0.json`** at the release root (`atlas_edits_2_5_0.id_map_bytes`): every 2.4.0 ID that moves, mapped to
  its 2.5.0 ID (518 entries: 72 source programs, 305 department and 141 general mixes; no construction set), with
  `base_release` 2.4.0 and `release` 2.5.0. A consumer holding older IDs translates through the earlier maps, then
  this one.
- **No generation document of its own.** The 2,270 programs with blocks keep them under their new IDs; the generation
  counts equal 2.4.0's. The writer requires the IECC commercial and detailed office `generation.json`, as the edits
  leave them, to equal `scripts.build_zone_recipes.build` over the edited release.
- **`LICENSE`, `LICENSE-DATA`** (unchanged texts) and the delta's `README.md`.
- **The writer** is the tagged `# >>> release 2.5.0` block of `scripts/atlas_delta.py`. The blocks of 2.4.0 and earlier
  are unchanged, so each earlier manifest's pin of the file still holds (`pinned_writer`), and `--check --release 2.4.0`
  still rebuilds 2.4.0. `input_sha256` pins the writer as 2.5.0 wrote it, `scripts/atlas_edits_2_5_0.py`, the two edit
  modules whose helpers it imports, `scripts/conditioning_sides.py`, its input
  (`data/program-inputs/conditioning-sides-v1.json`), the new lock `sources/conditioning-sides-lock.json`, both licence
  files and the 2.4.0 manifest.
- **Counts.** `counts.moved_ids` names the ID map. *Agent decision:* `counts.conditioning_sides` gives the source
  programs with a side not conditioned (72; 60 cooling sides and 47 heating sides), those with mixed service left
  unchanged (2) and the mixes by coverage (373 full, 69 partial, 4 unknown). The other counts are 2.4.0's.
- **The release-record program schema 1.1.0** (`schemas/atlas-release-program-v1.1.schema.json`) validates the records
  of every release (ADR 0063 section 2.3).

## 2. Export contracts

The exporters read release 2.5.0 (`scripts.atlas_exports.IN_TREE`); its exports take Program JSON **6.2.0**
(`scripts.atlas_contracts.PROGRAM_BY_RELEASE`, ADR 0063 section 2.4). Detailed constructions 5.0.0, unified 4.0.0,
source-model constructions 2.0.0 and building services 1.0.1 are unchanged. Every export names `atlas-release-2.5.0`.
Release 2.4.0 exports by name (`--release 2.4.0`) in Program JSON 6.1.0, which refuses a record with a coverage.

## 3. The site

The site builds release 2.5.0. A program page shows a *Conditioning* fact where the record states its sides
(`heating only (cooling not_conditioned: no source equipment serves it)`) and, for a mix, its setpoint coverage
(`setpoint coverage heating 1.000, cooling 0.303`); the exports' `nulls` and `controls` show the rest. The site index
(`site-manifest.json`, ADR 0058) carries no setpoint and is unchanged in shape; its compositions list the moved IDs.
The Pages artifact must stay under GitHub's 1 GB limit (`scripts.site_check`): the full 2.5.0 site built locally
before the merge (`python -m scripts.suite_site`, `mkdocs build --strict`, `site_check --require-complete`) measured
940,091,624 bytes in 30,822 files, about 1.7 MB more than 2.4.0's 938,382,966; the headroom is about 60 MB. The LOD pages translate the study's 2.4.0 IDs through `id-map-2.5.0.json` (ADR 0050); `data/lod-recommendations/`
does not change in this stage.

## 4. The generator: atlas-schedules 4.1.2 (agent decision)

As for 4.1.1 (ADR 0062 section 4): the generator's code does not change (it already averages setpoints over the members
that have them and reads a known null as no slot), but the wheel bundles the generator view of the newest release, and
that view changes: 518 program IDs move, and the generated cooling setpoint of a heated-only program or mix side is gone.
**`atlas-schedules` 4.1.2**, a patch: 4.1.0's code, whose wheel bundles the generator view of release 2.5.0. The 2.5.0
manifest's `generator` names 4.1.2 (wheel `atlas_schedules-4.1.2-py3-none-any.whl`, tag `atlas-schedules-v4.1.2`,
request schema 4.0.0, reads release 2.x and generation 1.x). The pairing of ADR 0049 item 4 gains a row.

## 5. Release assets

The `v2.5.0` GitHub release carries what 2.4.0's did (ADR 0062 section 5): `atlas-release-2.5.0.zip` (the `v2.0.0/` to
`v2.5.0/` folders), `atlas-release-2.5.0.manifest.json` and `id-map-2.5.0.json` byte for byte, listed in
`SHA256SUMS.txt` (`.github/workflows/atlas-data-release.yml`). The `atlas-schedules` 4.1.2 wheel and sdist go on their
own release, `atlas-schedules-v4.1.2`, with its `SHA256SUMS.txt` (`atlas-schedules-release.yml`), as 4.1.1's did: the
`v2.4.0` release carries no wheel.

## 6. Consequences

- Consumers move to release 2.5.0 and Program JSON 6.2.0 and re-key stored 2.4.0 IDs through `id-map-2.5.0.json`. What
  they read anew is in [`docs/bemgen-handoff-release-2-5-0.md`](../bemgen-handoff-release-2-5-0.md).
- `atlas-schedules` 4.1.2 is the generator to pin for 2.5.0 IDs.
- CI checks every delta: `atlas_delta --check` for 2.1.0 to 2.5.0, `build_zone_recipes --check` and
  `conditioning_sides --check`. The data-release workflow verifies 2.4.0 as well.
- Later releases follow the same pattern: a tagged block after this one, its own names for its edits, inputs and ID map.
