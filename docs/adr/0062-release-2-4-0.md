# ADR 0062: Release 2.4.0 (PNNL prototype corrections, Program JSON 6.1.0, atlas-schedules 4.1.1)

Status: accepted (2026-11-01; stage REL-A2 of the 2026-10-31 review, round 2). It publishes what stage AT4 merged as
source changes ([ADR 0060](0060-release-2-4-0-pnnl-prototype-corrections.md), the data;
[ADR 0061](0061-program-json-6-1-0-unoccupied-lighting-cap.md), the contract) and follows the mechanics of release 2.3.0
([ADR 0059](0059-release-2-3-0.md)). Decisions marked *agent decision* are this stage's.

## 1. The delta

Release 2.4.0 is a delta on 2.3.0 (ADR 0036 section 2, ADR 0046): `data/atlas-releases/v2.4.0` holds 2,942 files and
the manifest, and `removed` lists 2,301 paths of 2.3.0. The writer is `python -m scripts.atlas_delta --write --release
2.4.0`; `--check` rebuilds every file from its inputs and requires every program view to assemble (2,847).

- **The record edits** of ADR 0060: `scripts.atlas_edits_2_4_0.edit(files('2.3.0'))` gives the 2,938 files it changes or
  adds and the 2,301 paths it removes, the old names of the programs whose IDs move. The citing files follow the new IDs:
  the `generation.json` blocks, `services.json` beneficiaries, `definition-map.json` and `exporter-inputs.json`.
  - the unoccupied lighting cap on every known `lighting_controls` block: the rule on 19 90.1-2019 programs, an
    explicit null with its reason on 1,875;
  - the PNNL lighting power of the 11 90.1 whole-building office programs;
  - 84 PNNL 90.1 elevator and kitchen reach-in services in 36 folders.
- **`id-map-2.4.0.json`** at the release root (`atlas_edits_2_4_0.id_map_bytes`): every 2.3.0 ID that moves, mapped to
  its 2.4.0 ID (`ids`, 2,301 entries: 1,894 source programs, 296 department and 111 general mixes; no construction set),
  with `base_release` 2.3.0 and `release` 2.4.0. A consumer holding 2.2.0 IDs translates through `id-map-2.3.0.json` and
  then this file.
- **No generation document of its own.** The edits add no block; the 2,270 programs with blocks keep them under their
  new IDs, and the generation counts equal 2.3.0's (189 folders, 2,847 views, 507 services, 219 configurations). The
  writer requires the 99 IECC commercial and detailed office `generation.json`, as the edits leave them, to equal
  `scripts.build_zone_recipes.build` over the edited release, and gates them as `build_zone_recipes --check` does.
- **`LICENSE`, `LICENSE-DATA`** (unchanged texts) and the delta's `README.md`.
- **The writer** is the tagged `# >>> release 2.4.0` block of `scripts/atlas_delta.py` (ADR 0059 section 8). The blocks
  of 2.3.0 and earlier are unchanged, so each earlier manifest's pin of the file still holds (`pinned_writer`). The block
  keeps 2.3.0's names (`ID_MAP`, `EDIT_INPUTS`, `edits_2_3_0`) and adds its own (`ID_MAP_2_4_0`, `EDIT_INPUTS_2_4_0`,
  `edits_2_4_0`), so `--check --release 2.3.0` still rebuilds 2.3.0 from its own inputs. `input_sha256` pins the writer
  as 2.4.0 wrote it, `scripts/atlas_edits_2_4_0.py`, `scripts/atlas_edits.py` (whose helpers it imports), its three
  inputs (`data/program-inputs/unoccupied-lighting-cap-v1.json`, `pnnl-lighting-power-exceptions-v1.json`,
  `pnnl-building-services-v1.json`), both licence files and the 2.3.0 manifest.
- **Counts.** `counts.moved_ids` gives the moved programs and names the ID map. *Agent decision:* `counts.services` is
  counted over the resolved release (1,635, 2.3.0's 1,551 and the 84 new; the writer refuses any other sum), since the
  count carried from the base would be stale, and `counts.unoccupied_lighting_cap` gives the programs with a rule (19)
  and with a null rule (1,875). The other counts are 2.3.0's: no program, set or folder is added.
- `release_editor --check` also re-derives every 2.4.0 program ID (read with its generation block) and every set ID, and
  none moves.

## 2. Export contracts

The exporters read release 2.4.0 (`scripts.atlas_exports.IN_TREE`), and its exports take the contracts of ADR 0061
(`scripts.atlas_contracts.PROGRAM_BY_RELEASE`):

| Contract | Version | Schema |
| --- | --- | --- |
| Program JSON | **6.1.0** | `schemas/program-json-v6.1.schema.json` |
| Detailed constructions | 5.0.0 | `schemas/construction-json-v5.schema.json` |
| Unified constructions | 4.0.0 | `schemas/construction-equivalent-v4.schema.json` |
| Source-model constructions | 2.0.0 | `schemas/construction-source-model-v2.schema.json` |
| Building services | 1.0.1 | `schemas/building-services-v1.schema.json` (the 90.1 folders now export services) |

Every export names `atlas-release-2.4.0`. The site, the generator and the exporters default to 2.4.0. Release 2.3.0
exports by name (`--release 2.3.0`) in Program JSON 6.0.0.

## 3. The site

The site builds release 2.4.0, unchanged in its code. The Pages artifact must stay under GitHub's 1 GB limit; the 2.3.0
site was 931 MB. The full 2.4.0 site built locally before the merge (`python -m scripts.suite_site`, `mkdocs build
--strict`) measured 938,382,966 bytes in 30,737 files, under the 1,000,000,000-byte ceiling that `scripts.site_check`
enforces (about 7 MB more than 2.3.0, from the new evidence rows, cap fields and services). The headroom is about 62 MB;
a later release that would pass the ceiling must slim the site before it deploys.

## 4. The generator: atlas-schedules 4.1.1 (agent decision)

**Context.** The generator's code does not change with this release: the edits add no block and no recipe kind, and
requests and bundles stay schema 4.0.0. But the `atlas-schedules` wheel bundles the generator view of the newest
release (ADR 0051 section 4), and that view changes: 2,301 program IDs move, and the 11 90.1 whole-building offices are
generated with their PNNL lighting power (a bundle's amplitude and annual total use the record's value, ADR 0055
decision 7). A request in 2.4.0 IDs fails against the 4.1.0 wheel's bundled 2.3.0 view, and a wheel built from this tree
as 4.1.0 would differ from the published 4.1.0 wheel under the same version.

**Decision.** `atlas-schedules` **4.1.1**, a patch: 4.1.0's code, whose wheel bundles the generator view of release
2.4.0. The 2.4.0 manifest's `generator` names 4.1.1 (wheel `atlas_schedules-4.1.1-py3-none-any.whl`, tag
`atlas-schedules-v4.1.1`, request schema 4.0.0, reads release 2.x and generation 1.x). The quick start, the README and
the example requests move to 4.1.1 and 2.4.0 IDs; the request schema's example ID is re-keyed (an editorial revision of
`request-v4`). The pairing of ADR 0049 item 4 gains a row: 4.1.0 bundles 2.3.0, 4.1.1 bundles 2.4.0.

*Alternative:* keep 4.1.0 and have 2.4.0 consumers point `ATLAS_RELEASES` at the extracted archive. Rejected: the
installed wheel would answer 2.3.0 IDs by default, and two different 4.1.0 wheels would exist.

## 5. Release assets (agent decision)

The `v2.4.0` GitHub release carries `atlas-release-2.4.0.zip` (the `v2.0.0/` to `v2.4.0/` folders, as before) and, new,
the release manifest as `atlas-release-2.4.0.manifest.json` and `id-map-2.4.0.json`, byte for byte as in the release
folder, all three listed in `SHA256SUMS.txt` (`scripts.build_release_assets.published_files`; the data-release workflow
attaches every `.json` beside the archive). A consumer can pin the manifest and translate IDs without the archive.
Releases before 2.4.0 publish the archive alone, as they did.

## 6. Consequences

- Consumers move to release 2.4.0 and Program JSON 6.1.0 and re-key stored 2.3.0 IDs through `id-map-2.4.0.json`
  (BEMGen stage REL-B2). What they read anew:
  - `lighting_controls.unoccupied_lighting_cap`, `{rule, evidence_id}` on every known block; `rule` is the object of
    ADR 0061 section 2 or null, with the null's reason at `nulls["/lighting_controls/unoccupied_lighting_cap/rule"]`;
  - the 90.1 building services: zone services in the beneficiary program's `building_service_ids` (zones of that
    program), building-level services (no beneficiary, `assignment` `building_level`, all heat lost) only in the folder's
    building-services export;
  - the PNNL lighting power of the 11 offices, in the loads as before.
- `atlas-schedules` 4.1.1 is the generator to pin for 2.4.0 IDs.
- CI checks every delta: `atlas_delta --check` for 2.1.0 to 2.4.0, and `build_zone_recipes --check`. The data-release
  workflow verifies 2.3.0 as well.
- Later releases follow the same pattern: a tagged block after this one, its own names for its edits, inputs and ID map,
  and an ID map named by its release when IDs move.
