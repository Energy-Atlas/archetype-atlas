# ADR 0066: Release 2.6.0 (unconditioned attics: unified constructions 4.1.0 and the corrected InteriorCeiling)

Status: proposed (2026-11-09; branch `codex/release-2-6-0`). It publishes the contract and the record correction of
[ADR 0065](0065-unconditioned-attic-boundaries.md) (section 4: "a delta release (2.6.0) under ADR 0036 / 0046"), at the
repository owner's request for a new release with the unconditioned-attic repair, and follows the mechanics of release
2.5.0 ([ADR 0064](0064-release-2-5-0.md)). Decisions marked *agent decision* are this stage's.

## 1. The delta

Release 2.6.0 is a delta on 2.5.0 (ADR 0036 section 2, ADR 0046): `data/atlas-releases/v2.6.0` holds 36 files and the
manifest, and `removed` lists the 24 paths of 2.5.0 whose construction sets move. The writer is
`python -m scripts.atlas_delta --write --release 2.6.0`; `--check` rebuilds every file from its inputs and requires every
program view to assemble (2,847).

- **The record edit** of ADR 0065 section 3: `scripts.atlas_edits_2_6_0.edit(files('2.5.0'))`. In every unified context
  with an openstudio-standards attic (the `Attic` space type of the 90.1 and DOE Ref sets) the rule
  `attic_boundary._ceiling_correction` reports `corrected` for all 568 contexts of 24 sets, `unresolved` for none.
  - `components.InteriorCeiling.derivation` becomes the corrected derivation: the attic-paired ceiling area (the attic
    `InteriorFloor` contributor's area) leaves the one building-default contributor. In all 568 contexts the remaining
    reference area is 0, so the derivation is `unique_source_recipe_without_reference_exposure` with weight 1, as for any
    recipe the source has without exposure. The `InteriorCeiling` assembly, the detailed rules (the building-default
    `Typical Interior Ceiling` rule), every other component and every library record are unchanged.
  - `provenance.interior_ceiling_correction` keeps what the record replaced: `replaced` (the derivation releases 2.0.0 to
    2.5.0 stored), `paired_ceiling_area_m2`, `pointer`, `status: corrected`, `reason`, `evidence_ids` and `decision`
    (this ADR). *Agent decision:* the record keeps the replaced value with the correction, as ADR 0046 section 11's
    `source_boundary_correction` and ADR 0063's replaced schedules do, so the change stays traceable in the record and
    the export can state it (section 2). *Alternative:* the replaced value only in this ADR and the 2.5.0 folder.
  - The OpenStudio interzone-resolution evidence row (`attic-evidence-16def2`, the row the 4.1.0 export already cited:
    `ForwardTranslator::resolveMatchedSurfaceConstructionConflicts` at OpenStudio `86d7e215`, file SHA-256 from
    `sources/construction-interzone-lock.json`) joins `evidence/commercial/<template>/library.json` of the five templates,
    and each corrected context's unified evidence list cites it.
  - Values follow the set's storage (ADR 0036 section 6): in 19 sets the corrected component and the provenance member are
    shared by every unified context and stay in the set's common part; in the five generic office sets (the office set
    covers several references, not all with an attic) each corrected context gets its own value through the set's value
    table.
- **IDs.** Construction set IDs hash the set (ADR 0046 section 8), so the 24 corrected sets move; no program, schedule,
  service, assembly or material ID moves. `id-map-2.6.0.json` at the release root (`atlas_edits_2_6_0.id_map_bytes`) maps
  the 24 set IDs, with `base_release` 2.5.0 and `release` 2.6.0. The citing files follow (`scripts.atlas_edits.follow_ids`):
  the DOE Ref small-hotel evidence files, which name their sets, and `id-map-2.3.0.json`, whose two DOE Ref small-hotel
  targets now name the 2.6.0 sets, as release 2.5.0 rewrote the earlier maps' program targets. A unified context ID is
  the set ID with the context key, so it moves with its set.
- **No program, schedule, service or generation document changes.** The writer refuses any; the generation counts and the
  service count equal 2.5.0's, and the IECC commercial and detailed office `generation.json` still equal
  `scripts.build_zone_recipes.build` over the edited release.
- **`LICENSE`, `LICENSE-DATA`** (unchanged texts) and the delta's `README.md`.
- **The writer** is the tagged `# >>> release 2.6.0` block of `scripts/atlas_delta.py`. The blocks of 2.5.0 and earlier
  are unchanged, so each earlier manifest's pin of the file still holds (`pinned_writer`). `input_sha256` pins the writer
  as 2.6.0 wrote it, `scripts/atlas_edits_2_6_0.py`, `scripts/atlas_edits.py` (whose `Tree` and `follow_ids` it uses),
  `sources/construction-interzone-lock.json`, both licence files and the 2.5.0 manifest. *Agent decision:*
  `scripts/attic_boundary.py`, whose recognition and correction rule the edit applies, is not pinned: it is also the
  4.1.0 exporter, and a pin would freeze the exporter with the release. `--check` still fails on any change of the rule
  that changes a release file, because it compares every file byte for byte.
- **Counts.** `counts.moved_ids` names the ID map (24 construction sets, no program).
  *Agent decision:* `counts.interior_ceiling_corrections` gives the corrected sets (24) and contexts (568) and the
  unresolved contexts (0), and `counts.unified_attics` the unified contexts whose 4.1.0 export states an attic (926:
  568 openstudio-standards, 342 IECC, 16 ResStock), so the manifest says what the new contract covers. The other counts
  are 2.5.0's.

## 2. Export contracts

The exporters read release 2.6.0 (`scripts.atlas_exports.IN_TREE`). Its unified exports take **unified constructions
4.1.0** (`schemas/construction-equivalent-v4.1.schema.json`, ADR 0065 section 2; `scripts.atlas_contracts.UNIFIED_BY_RELEASE`)
for every unified context: `Release.construction(set, context, 'unified')` forms the 4.0.0 document, then
`scripts.attic_boundary.augment` adds `attics`, `components.<role>.attics` and `export_corrections` where the context has
an attic. A context without one is the 4.0.0 document with `schema_version` 4.1.0 (an additive minor, so every 4.0.0
field keeps its meaning). Program JSON 6.2.0, detailed constructions 5.0.0, source-model constructions 2.0.0 and building
services 1.0.1 are unchanged. Every export names `atlas-release-2.6.0`. Release 2.5.0 exports by name (`--release
2.5.0`) as before: unified 4.0.0, or 4.1.0 with the correction applied at export (`--attics`).

**`export_corrections` from a record that carries its correction** (*agent decision*). In 2.6.0 the stored derivation is
already corrected, so the exporter does not subtract the paired area again: it states the record's correction, with
`stored` the derivation the record replaced (the value releases 2.0.0 to 2.5.0 stored) and `corrected` the one 2.6.0
stores, after checking that the ADR 0065 rule applied to `stored` gives the stored derivation, the same paired area and
the same evidence. The provenance member is not repeated in the export. The 4.1.0 documents of the 568 contexts therefore
equal the pre-release 4.1.0 exports of 2.5.0 except for the release label and the moved set IDs (section 5).
*Alternative:* drop `export_corrections` from 2.6.0, since nothing is corrected at export any more; rejected because a
consumer that compared 4.0.0 with 4.1.0 would lose the statement of what changed. The 4.1.0 schema's description of the
member ("a value the export corrects against the stored release record") reads, for 2.6.0, as the record's correction
against its earlier stored value; restating it would be a 4.1.0 schema revision, left to the owner (section 6).

## 3. The site

The site builds release 2.6.0. A construction page's unified button shows `Unified 4.1.0`, and the unified document of
an attic context carries the attic statement. The site index (`site-manifest.json`, ADR 0058) is unchanged in shape; its
construction entries name the moved set IDs. The LOD pages translate the study's IDs through the ID maps (ADR 0050), and
`data/lod-recommendations/` does not change in this stage.

## 4. The generator (agent decision)

No generator release. ADR 0049 item 4: a data release that rewrites recipes names the generator version that wrote them;
2.6.0 rewrites none (no program, schedule, service or `generation.json` changes), so its manifest names
**`atlas-schedules` 4.1.2**, whose wheel bundles the 2.5.0 generator view with the same recipes. A bundle generated with
the 4.1.2 wheel records release 2.5.0; one generated against the 2.6.0 tree records 2.6.0, with the same schedules. The
pairing table of ADR 0049 gains the 2.6.0 row. *Alternative:* `atlas-schedules` 4.1.3, 4.1.0's code bundling the 2.6.0
view, as 4.1.1 and 4.1.2 did; it would change only the bundled view's release provenance, and needs an owner tag.

## 5. Evidence of the delta

- The 24 sets and their 2.6.0 IDs are in `id-map-2.6.0.json`; for example `90-1-2019.small-office-detailed.construction-package.7eee9d`
  becomes `…ff7fc8`, `90-1-2007…b1ba8a` `…7fae32`, `doe-ref-1980-2004…8575fa` `…bdc90e` and `doe-ref-pre-1980…db34c2`
  `…14f979`.
- 90.1-2019 SmallOfficeDetailed 4A: `InteriorCeiling` reference area 511.156 m2 replaced by 0; the attic floor
  (`typical-wood-joist-attic-floor`, 511.156 m2) is the conditioned boundary, and the attic-omitted roof is U 0.11384 W/m2K
  (ADR 0065 section 2.1), unchanged.
- The 4.1.0 export of each of the 568 contexts equals the pre-release 4.1.0 export of release 2.5.0 (ADR 0065,
  `python -m scripts.attic_boundary --export`) in every field except `release`, `id`, `detailed_context_id` and
  `source.construction_set_id` (`tests/test_release_2_6_0.py` checks it for every corrected context against the 2.5.0
  export with the rule applied).

## 6. Consequences and open questions

- Consumers move to release 2.6.0 and unified 4.1.0, and re-key stored 2.5.0 construction set IDs through
  `id-map-2.6.0.json`. What they read anew is in [`docs/bemgen-handoff-release-2-6-0.md`](../bemgen-handoff-release-2-6-0.md).
- CI checks every delta: `atlas_delta --check` for 2.1.0 to 2.6.0. The data-release workflow verifies 2.5.0 as well.
- The release assets of the `v2.6.0` GitHub release are 2.5.0's kind (ADR 0064 section 5): `atlas-release-2.6.0.zip`
  (the `v2.0.0/` to `v2.6.0/` folders), `atlas-release-2.6.0.manifest.json` and `id-map-2.6.0.json`, with
  `SHA256SUMS.txt`, attached by `.github/workflows/atlas-data-release.yml` when the owner pushes the tag `v2.6.0`.
- Open for the owner: the ADR 0065 questions (plenum ceilings, attic air for a consumer that omits the attic, DOE Ref
  pre-1980's attic, ResStock gable walls, the film convention, IECC 2024); whether to restate the 4.1.0
  `export_corrections` description for records that carry their correction (section 2); and whether to cut
  `atlas-schedules` 4.1.3 (section 4).
- Later releases follow the same pattern: a tagged block after this one, its own names for its edits, inputs and ID map.
