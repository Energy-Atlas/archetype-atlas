# ADR 0027: Explicit generated physical-service owners

Status: accepted by the Task10 controller as Ruling17; implementation and native qualification remain separate. The approved detailed design is `restaurant-physical-service-owner-design.md` in the Task10 evidence folder. C4 public-helper fix is closed at `61a26e06f240b52427d3ecf2e9720eaf4bc2c791`, immutable v0.5.1; no older artifact or Program JSONv3 is rewritten.

Some source service definitions have no programme beneficiary, including the FullServiceRestaurant code-era absolute booster. A physical fixture cannot be represented by an invented Kitchen or by putting a service ID into `program_id`. Source Kitchen `loads[]`/`service_ids[]` aliases also cannot become two water draws. This ADR adds an explicit identity contract and retains caller physical bindings, original reference basis and source unknowns.

## Version and identity

Public `generate(params, seed)` keeps its signature. Absence of `params.schema_version` selects1.0.0. An explicit1.0.0 marker is removed only for validation against the unchanged v1.0 params schema; its output has the same science as omission. Only explicit1.1.0 selects the new schema. Unknown owner fields never select a version implicitly, and unsupported versions fail. The CLI envelope remains exactly `schema_version/params/seed`; envelope version must equal the effective params version. A1.1 request carries both1.1 markers; conflicting or missing1.1 params marker fails. API/CLI equivalence and strict old-version rejection are tested.

The1.1 ordered instance array is a strict discriminated union: `owner_kind: program` with `program_id`, or `owner_kind: physical_service` with exact `source_service_id` and caller `physical_id`. Foreign identity fields are forbidden. Common key/inputs/basis_bindings/operating_group fields retain their meaning.1.1 bundles use the same alternatives for source owners and their bindings; a mixed result has `owner_kind: derived_result` and its caller result label in `program_id`, explicitly a derived label. Services never have `program_id`. Legacy1.0 owners remain readable through their existing identity. Typed identity propagates scientific comparison keys/projections, bundle and nested reference validation, generic composition and source-parent projection, examples, coverage and own-runtime reproduction. No random stream is allocated merely because an owner is a service.

## Source records and links

Service recipes use existing resource kind `reference`, with strict keys `physical-service__<exact source service ID>`. Each record has the normalized immutable `services.json` pointer/hash, original primary source/lock evidence, exact service shape/ID, source schedule rules, native method context and original budget. This does not expand the resource-kind vocabulary or manifest version, and creates no fake programme resource.

A programme declares exact required active service alias links. The physical service alone owns its water slot/binding. The programme retains a truthful typed link and channel coverage receipt to that actual service resource/owner; no duplicate local schedule/demand and no silently omitted active channel. Missing link reports `requires_binding` with programme/channel/service context. Declared link method closure is distinct from a fully bound runnable example/reference proof. The same source SID across views names one source path; caller physical IDs distinguish actual fixtures. Reviewed Kitchen omissions remain omissions. An explicit external source-defined service can accompany a reviewed programme with an adaptation receipt; it does not invent a reviewed Kitchen or allocate water to Dining.

## Budget and whole-fixture semantics

Main source magnitudes and original annual targets stay per floor area. Caller fixture extent is the actual Kitchen area times its actual multiplier, with separate original operand receipts, applied once when converting the whole fixture to a physical mixed result; service multiplicity is1. A standalone main fixture preserves its original per-area target before generated amplitude binding. Booster remains absolute1.33USgal/min, extent1 and multiplicity1, independent of area. Unused133/40USgal/h branches and the Full.6 heater-energy fraction do not enter water volume.

`physical_id` identifies a real fixture; `source_service_id` identifies its source definition. Repeated links to one physical fixture emit one binding; distinct physical IDs using one source definition remain distinct fixtures. Conflicting source/extent/target/trajectory/metadata for one physical ID fail. Only source-qualified `mode: whole` is supported. Components and already-allocated shares require missing source total/allocation proof and remain `requires_binding`; no guessed sharing or scaling of absolute volumes.

Water volume remains a water carrier, separate from source heater gas/electric energy. Known service host `building_service` denotes physical scope; original `zone_heat_assignment: unresolved`, beneficiary/fixture-location distinctions, target temperature and empty thermal-effects metadata stay explicit. No inlet temperature, system efficiency, zone or heat fractions are inferred.

## Native context and qualification

Restaurant source water fixtures are unattached to a space. Pinned Standards0.8.6 `parametric.rb:309-325` registers their eligible Ruleset against whole-model HOO and skips a previously registered schedule key. Full main and booster share one source schedule transform but retain two physical fixture budgets. Qualification must execute those actual registration/apply methods and compare source profiles/rules/design days/hourly values, rather than apply lighting/plug BPR or occupancy adjustment to water.

The2013 actual source-geometry/People pilot proves Full .1/1/100 normalized carrier equivalence at seeds42/51 only for that source context. Quick normalized carriers fail: actual weighted People/source round6 produce weekday HOO7–23, normalized probes7–24, with different water outputs even after modified HOO matches. Preserve Quick's original actual People/area/multiplier/order and arithmetic. Caller physical fixture extent and explicitly labelled source-reference HOO context are separate operands/receipts. Other templates/views and all13 restaurant fixture definitions need independent closure. A common schedule name is insufficient qualification.

The source v33 ten draws and strict-CDF tails remain unnormalized contextual source failures. Services in a qualified restaurant group reuse its exact source/configuration/HOO context without extra draws. Missing carrier/context/fixture operands remain explicitly `requires_binding`. No restaurant-pair batching or native whole-prototype equivalence is approved by this ADR.

Ruling17 cost: version/identity misdispatch or a twice-applied physical extent can corrupt ownership/conservation while plausible arrays still emit. Strict version/identity/API/CLI/reference tests, unequal physical extents, alias/dedup conflicts, original volume targets at multiple seeds, per-template native/source comparisons and offline own-artifact proof guard this boundary. Full Task10 extraction remains active.

## Ruling18: required-link closure and separate service selection

Separate wire selectors, explicit closure receipts, strict complete fixture proof and programme-only/explicit-plus-linked/shared-alias/zero/conflict/missing-owner/unrelated-booster/annual-volume/reference regression guard the boundary. ## Ruling19: explicit view-specific HOO context

Every restaurant realization binds an exact `source_hoo_configuration_id` qualified for its family, template, source/reviewed view, calendar, People operands/order, locked geometry and operating group. Source configurations use original Dining and Kitchen People. Reviewed configurations use reviewed Dining and actual remaining reviewed rooms only; omitted Kitchen People remain omitted. Each is independently captured through the pinned native inference/registration/apply methods. Missing context requires binding and conflicting contexts within one operating group fail.

An external source main or booster fixture may use the reviewed model-wide HOO only with an explicit crossview prototype adaptation receipt. Its original source service ID/path/profile/annual budget/beneficiary and area provenance stay intact. A reviewed HOO model is not the full original source prototype, and no Kitchen programme, People object or geometry is invented. Caller fixture extent stays separate from the labelled HOO reference context.

Ruling19 cost: a reviewed-subset HOO can misrepresent the full source building or misattribute an external fixture. Paired per-template source/reviewed native HOO/registration/rule/special/hourly comparisons, strict configuration/group matching, unchanged original annual volume/source origin and explicit adaptation scope guard the boundary. No original stock/population equivalence or restaurant pair shipment is approved.

Only method-consumed dependencies enter the exact restaurant group fingerprint. Configuration/view/People/calendar/source clock/selected caller policy remain strict. This does not change Office/Warehouse fingerprint semantics or permit a used/foreign weather operand.

Public composition of separately generated bundles compares the exact consumed group context and operating receipts. ## Original requirement authority at bundle validation

A bound alias is not the authority for whether a programme requires a source service. Every non-physical v1.1 owner retains a mandatory independent `required_service_links` inventory copied from its compiled original recipe before alias binding. Original requirements preserve exact source SID, channel, required flag, original programme demand and evidence. Programmes without external requirements and derived results carry explicit empty inventories. Only a validated v1.0 input can receive an empty inventory during version upgrade; an absent or malformed v1.1 inventory is rejected. Physical owners do not invent programme requirements.

Actual bound links must cover the inventory one-to-one. Original demand/evidence must close against the physical source definition, original beneficiary, source family/template and assignment. The documented `program_service` to `building_service` transition changes only load scope; all other original load fields remain equal. Generated volume demand retains water fuel and physical building-service host, with original unresolved heat assignment. Its original target is recomputed with the existing canonical budget function and retained original water Ruleset/calendar, then compared with the physical binding and alias target receipt. Configuration and operating-group identity remain strict.

The correction addresses an actual pre-shipment self-review failure where a coherent Main-to-Booster alias substitution passed while original Main evidence remained unchanged; the independent inventory also prevents dropping all aliases from erasing required-source knowledge. No source/RNG/numerical method or annual target changes. This is retained source-reference validation, not cryptographic attestation against rewriting every source/provenance object. Standalone validation/composition adds no repository or default-resource lookup. Old v1.0 and immutable archives remain unchanged.


The C5 inventory-to-alias relation is qualified for exactly one physical main fixture per required source SID/channel in each restaurant context. It does not certify a general one-to-many mapping for LargeOffice cores or repeated Hotel rooms that share a source SID. Those later families need explicit physical coverage and source-parameter versus aggregate-budget qualification; selecting one fixture, merging physical IDs or multiplying canonical programme budgets is not implied by this contract.
