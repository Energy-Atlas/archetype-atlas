## Purpose and exact source scope

The next runtime must represent a real water fixture whose source definition has no programme owner. In particular, a FullService booster is not a Kitchen load and reviewed Kitchen omissions cannot create Kitchen programme IDs. The candidate pair has 46 existing programmes, no compositions and 13 actual service definitions. Batching the pair into one release is a separate decision after per-family qualification.

The ten main definitions are Full `service-8e7e12117b8be2498b0ffdd7`, `service-24ad7408506ea3d448dc35d0`, `service-fd85cf8e5a8b379d26265f0a`, `service-b8a1e9bdda66f9a7772291b9`, `service-818680b91c14e0260af81f7d`; Quick `service-feab40348c3705412b1d8a91`, `service-1981fa97b9fd7d47efcf39dd`, `service-362e595a9b6d9f3c4a04336c`, `service-72c0a449ebbe7c1be0679ffe`, `service-5b83136ba2e7cbc86fb5fc14`, in template order 2007/2013/2019/DOE1980/DOEpre1980. ## Interface choices and recommendation

Reject fake programme IDs: neither a source service ID in `program_id` nor a generated Kitchen programme is truthful. A separate top-level services array is possible, but needs another explicit interleaving/order contract and separate mixture-key namespace. Recommend one ordered instance array with a strict versioned identity union, so source group allocation and request order remain explicit.

Existing unversioned request v1.0 and emitted bundle v1.0 retain their exact programme-only contract. Direct public `generate(params, seed)` selects v1.0 when `params.schema_version` is absent; it selects v1.1 only when that marker is exactly `1.1.0`. An explicit `1.0.0` marker is accepted by the dispatcher, removed only for validation against the unchanged v1.0 params schema, and has the same scientific output as omission. Every other marker fails. Unknown owner fields never select a version implicitly. v1.1 requires its marker and a separate schema; do not relax v1.0 required identity.

The CLI envelope remains exactly `schema_version/params/seed`. Its envelope version must equal the effective params version (absent params marker means 1.0). Thus a v1.1 CLI request must carry both markers `1.1.0`; a v1.1 envelope with unmarked params, or v1.0 envelope with v1.1 params, fails before generation. CLI forwards the same params object and seed to the unchanged callable signature. Test API/CLI equality, absent-versus-explicit v1.0 equality, conflicting markers and unknown versions; no implicit CLI injection hides a direct-API difference. Development example/release/reproduction wrappers follow this matching rule.

v1.1 instances have either `owner_kind: program` plus `program_id`, or `owner_kind: physical_service` plus `source_service_id` and caller `physical_id`, with the foreign identity fields forbidden. Common fields are `key`, `inputs`, `basis_bindings`, `operating_group`. Services use the same declared resource identity and only exact supported service recipes. Programme instances may supply `service_links` from their exact source service ID to an explicit service-owner key. The Kitchen `loads[]`/`service_ids[]` aliases become one link to one physical demand; neither creates a second binding. Missing links/physical extent yield `requires_binding` for that active service, without replacing programme-only load channels or inventing an owner. A service-only v1.1 request is permitted once its complete HOO context is bound.

v1.1 bundle constituents and bindings use the same discriminated identity: programme owners retain `program_id`, service owners carry `source_service_id` and no `program_id`. Derived mixture owners retain the caller result label in `program_id` with explicit `owner_kind: derived_result`; it is a derived label, not a source programme. The programme's service link is a reference, not another load owner. Every emitted service demand belongs to the actual physical-service constituent, with its exact source definition locator, path, beneficiary IDs, ownership/assignment, fixture identity and alias receipts. Old bundles remain readable as implicit programme owners.

An identity helper must propagate to scientific binding keys, comparison `_reference_projection`, `scientific_constituents`, unbound-slot keys and bound-slot exclusion; bundle owner/reference validation; generic composer request reconstruction; indexed member/reference closure; resource coverage/native capture/certificate/example/reproduction consumers. Generic composition validates actual typed incoming owners rather than fabricating programme-only instances. Mixture membership remains by unique instance key. Schedule IDs remain `schedule_id(key, slot)`; no scientific identity collision is hidden by the new type. v1.0 public/generic behavior and immutable old packages stay unchanged. Public `generate(params, seed)` remains the same callable.

## Physical budget and ownership contract

Keep each main source magnitude and annual target **per floor area**, with explicit physical extent `floor_area = actual Kitchen area × actual source space multiplier`, carrying separate original area and multiplier receipts. Apply that extent exactly once when converting a whole physical fixture into a mixed physical result; service multiplicity is 1. The service descriptor `mode: whole` owns that exact extent. It overrides informational programme participation weights under the existing instantiate-once policy. Do not also multiply the source magnitude or target by area before binding. Native construction may need the absolute flow for its WaterUseEquipmentDefinition; that development construction is separately receipted and does not change the runtime reference basis.

Booster magnitude/annual target remains absolute: 1.33 US gal/min = 8.390996121200001e-5 m3/s, explicit absolute extent 1 and multiplicity 1. Full main retains 0.08860759494 US gal/h/ft2 and Quick main .032 US gal/h/ft2. The unused 133/40 gal/h alternatives and Full .6 heater fraction never enter fixture volume. Each original schedule integral is recovered before random transformation or amplitude binding. Volume uses water as its carrier, not the source heater's gas/electric energy; heater metadata and 60/82.22222222222221 C fixture temperatures remain separate. Missing inlet temperature/efficiency/system heat is not filled.

`physical_id` identifies a caller's actual fixture. `source_service_id` identifies its exact source definition. Two different physical IDs using the same source main definition are two fixtures. Multiple programme aliases of one physical ID emit one binding and preserve all links. Reusing one physical ID with a different source definition, extent, original target, group trajectory or service metadata fails contextually. Source main beneficiary is the exact Kitchen programme; that is not a thermal-zone attachment. Booster beneficiary remains empty. Host `building_service` denotes the known physical scope only; `zone_heat_assignment: unresolved`, empty physical fixture locations and original source assignment remain explicit. No thermal zone or heat fractions are inferred. If runtime host vocabulary needs a new unresolved service-host value, use a schema/ADR declaration rather than pretending an existing zone was supplied.

Only whole-service ownership is proposed now. Component/already-allocated service requests continue `requires_binding` until source total, allocation and upstream already-allocated receipts/methods are qualified. No guessed sharing or floor-area scaling of absolute booster service is added. Reviewed Dining/Attic may explicitly accompany a service owner drawn from the same source template, but the cross-view receipt must say external physical service from the source definition; it does not add a reviewed Kitchen or allocate its loads to Dining. Programme view and service-definition view remain distinct.

## Native qualification and seeds

Begin with actual 2013 source Dining/Kitchen/Attic in each family, using source People schedules, names, actual bound design-people/area/multiplier operands or a separately native-compared labelled normalized carrier. A common schedule name alone is insufficient: native round6 weighted aggregation must be tested. The source water helper makes unattached fixtures; Standards0.8.6 `parametric.rb:309-325` selects whole-model HOO and skips a duplicate schedule key. Capture actual registration of Full main plus booster sharing one schedule, and Quick main, before claiming a runtime water transform. Record original and modified HOO, registration count/key, formula/profiles/rule order/design days, source-fixed versus transformed branch and all hourly arrays. The shared source water schedule has one transform, two original Full budgets and two physical fixtures.

Service owners join the exact bound restaurant commercial group, without extra RNG draws or a hidden source-programme instance. Require the same qualified configuration/HOO context, template and declared source-view adaptation. Preserve original ordered v33 draws and strict CDF tail errors; no normalization/retry. A service lacking its HOO group/carrier context remains `requires_binding`. Actual service transform qualification can use direct truthful native fixtures before this owner API exists.
