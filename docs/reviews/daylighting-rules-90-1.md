# 90.1 daylighting records vs the openstudio-standards rules

Evidence only (plan stage B2, user decision L-2). Generated by `python -m scripts.daylighting_rules_review` from release 2.0.0 and the openstudio-standards rules at the pinned revision (`sources/daylighting-rules-lock.json`); no value changes.

## What is compared

- **Records:** the `lighting_controls` of every 90.1 source program with a known record, and its `daylighting_by_climate` variants. They come from the PNNL prototypes (ADR 0044 agent decision 1).
- **Rules:** whether the template requires controls (`space_daylighting_control_required?`), the control type, stepped-control steps, minimum input-power and light-output fractions, and the illuminance setpoint (the space-type target, 375 lux where none, no controls where `na`).
- **Office whole-building programs:** the controlled lighting fraction against the non-geometry caps (`psa_nongeometry_fraction` plus `ssa_nongeometry_fraction`).
- **Not compared:** which zones get controls and the controlled fractions otherwise. They follow from the window geometry (daylit areas, the 150 W, 300 W and 20 ft² thresholds) and are geometry-dependent.

## Reading

- The PNNL prototypes and openstudio-standards are separate implementations of the same code rules; a difference here is a difference between the two sources, not an atlas error. The records keep the PNNL values (ADR 0044); this report is evidence for a consumer choosing between them.
- `stepped_control_steps` matters only for stepped control. The 2019 records carry the IDF field, which continuous-off control ignores.
